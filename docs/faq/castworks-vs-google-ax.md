# castworks 与 Google AX

## 对照范围

对照的两份设计：

- castworks：`../design/architecture.md` 与 `../design/modules/design-runcontroller.md` 描述的需求与设计。
- Google AX：Google 开源的声明式 Agent 编排运行时（[REF-google-ax](../references.md)），其 `Task`、`Workspace`、`Model` 资源与生命周期契约。

对照只覆盖需求与设计，不覆盖实现与成熟度。两者共同依赖的 Agent Substrate 能力（[REF-substrate](../references.md)）按 Substrate 的公开设计计入，并标注为底层能力而非 AX 自有设计。

重合度的口径是 AX 的设计要素覆盖 castworks 设计要素的比例。反向覆盖度单独给出。分值是设计判断，不是测量值。

## 结论

| 层次 | 重合度 | 口径 |
| --- | --- | --- |
| 问题域与定位 | 约 60% | 两端都处理 Agent 在沙箱中运行、工作区持久化、等待期间释放算力、依赖解除后恢复 |
| 核心机制 | 约 15% | 挂起与恢复的表层机制重合；等待原语、自动挂起决策、事件源闭环与协作层级在 AX 的设计中没有对应机制 |
| 正确性保证与安全约束 | 约 20% | 共享 Substrate 与关系数据库存储带来部分重合；失效判定、投递确认、工作区租约与零长期凭据边界没有对应机制 |
| 环境供给与编排能力（反向） | 约 35–40% | castworks 的设计覆盖 AX 设计要素的比例；AX 的声明式资源、环境模板与编排能力在 castworks 的设计中大部分没有对应能力 |

按 castworks 的设计要素计，AX 覆盖约 23%，区间 20%–28%。按 AX 的设计要素计，castworks 覆盖约 35–40%。两端面对同一问题域，重合集中在底层沙箱与生命周期，机制与控制权不同。

## 总体重合度是多少

按 castworks 的设计要素计，重合度约 23%。分值对权重敏感：以问题域为主计分接近 60%，以核心机制与正确性保证为主计分接近 15–20%。单一数字只在口径声明之后有意义。

逐维度的分值如下。分值仍是 AX 覆盖 castworks 的比例，最后一行的方向相反。

| 维度 | 覆盖度 | 方向 | 判断 |
| --- | --- | --- | --- |
| 定位与资源模型 | 55 | 并行 | 两端都以沙箱、持久化工作区、显式挂起与恢复为核心；AX 是声明式不可变资源，castworks 是长生命周期运行实例状态机 |
| 挂起与恢复决策、机制 | 24 | 并行 | 两端都有挂起与恢复；AX 由调用方显式触发并使用 Substrate 快照，castworks 由等待推导自动决策并在冻结、快照、销毁重建之间选择 |
| 等待与唤醒原语 | 6 | castworks 为超集 | AX 没有收件箱、唤醒信号、唤醒谓词、持久定时器与订阅 |
| Agent 协作层级与驱动器 | 23 | castworks 为超集 | AX 的 runner 契约只覆盖进程监督与探针；castworks 定义 L0/L1/L2、回合边界与恢复句柄 |
| 事件源闭环 | 6 | 设计取向相反 | AX 没有 LLM 网关、连接器、人类通道、审批与订阅 |
| 安全边界、凭据与网络出口 | 18 | 设计取向相反 | AX 以环境变量承载密钥，沙箱内进程以高权限运行；castworks 要求沙箱内零长期凭据与出口默认拒绝 |
| 控制面数据模型、一致性与失效判定 | 28 | 并行 | 两端都以 PostgreSQL 与每资源一把锁管理资源；AX 没有失效判定、两级投递确认与对账器 |
| 沙箱提供者、运行时集成与规模 | 31 | castworks 为超集 | AX 把快照、预热与路由唤醒委托给 Substrate；castworks 另外定义提供者能力集合与恢复准入 |

安全维度的分值取决于是否把 Substrate 的出口网关与凭据注入计入 AX 的能力。只计 AX 自有设计时为 18；计入 Substrate 委托能力后接近 30。方向判断不随口径改变。

## 哪些设计真正重合

以下为主要重合点，不构成穷举。

1. **沙箱生命周期与持久化工作区。** AX 的任务把持久目录挂载为 `/workspace`，由 Substrate 在挂起与恢复之间保留；castworks 的工作区是运行实例的持久化目录，跨沙箱代保留。两端都把工作区置于沙箱生命周期之外。
2. **挂起与恢复是一等操作。** AX 的 `ax.v1alpha1.AX` 服务定义 `SuspendTask` 与 `ResumeTask`；castworks 的运行实例状态机把挂起与恢复作为显式状态。
3. **控制面直接管理沙箱提供者。** AX 的 `ax-server` 直接调用 Substrate Control API 预配、挂起、恢复与删除 actor；castworks 的 `sandboxprovider` 承担同一职责。两端都不以 Kubernetes CRD 作为状态事实源。
4. **沙箱内 PID 1 守护进程与就绪探针。** AX 的 `runner.Run` 是任务容器的 PID 1，提供 `/healthz` 与 `/readyz`；castworks 的看守进程是沙箱 PID 1，同样以就绪探针参与恢复。
5. **入站请求触发恢复。** AX 的入站请求经 atenet router 按 `ate-target-actor` 头寻址，请求到达时先恢复挂起的 actor；castworks 的 Substrate 提供者路径同样经路由器调用 `/wake`，并让请求等待直到 `/readyz` 就绪。

## 挂起与恢复的设计差异

| 方面 | AX | castworks |
| --- | --- | --- |
| 决策者 | 调用方，经 `SuspendTask` 或 CLI 的 `suspend` | 控制面，在运行实例行锁内评估唤醒谓词后调用挂起决策函数 |
| 触发依据 | 显式命令 | LLM 在途请求、外部系统订阅、人类消息、审批决定与定时器的并集；没有依赖时不得挂起 |
| 机制集合 | Substrate 的 actor 快照加暂停 | 冻结、快照、销毁重建、不挂起；按沙箱提供者能力集合选择 |
| 挂起期间保留 | 由 Substrate 快照策略决定，任务容器在恢复后是新进程树 | 冻结保留内存；快照保留内存与文件系统；销毁重建只保留工作区与恢复句柄 |
| 恢复后续接 | 新容器挂载恢复后的 `/workspace`，runner 重新启动 `spec.command` | 冻结直接解冻；快照恢复同代续接；销毁重建以恢复句柄续接 Agent 会话 |
| 恢复准入 | 无队列，恢复由调用方或入站请求直接触发 | 按机制限速、按唤醒原因排定优先级、按老化提升 |

重合的是「存在挂起与恢复」，不重合的是「谁决定、依据什么、恢复到哪一步」。

## AX 是否提供等待与唤醒原语

不提供。AX 的资源模型没有收件箱、唤醒信号、唤醒谓词、等待条件、持久定时器与订阅。AX 的恢复触发只有两种来源：显式 `ResumeTask` 调用，以及 atenet router 在入站请求到达时恢复 actor。两者都回答「谁来敲门」，不回答「Agent 等待的依赖是否已经解除」。

castworks 的等待是控制面从持久化事实推导的条件集合。可投递事件进入收件箱，不进入收件箱的解除信号记为唤醒信号，唤醒谓词在运行实例行锁内评估。LLM 响应完成、外部系统事件、人类消息、审批决定与定时器共用这一原语。

## AX 是否覆盖事件源闭环

不覆盖。AX 的资源模型没有 LLM 网关、连接器、外部系统定义、订阅、审批决定与人类通道。AX 的 `Model` 资源描述模型提供方、模型标识、生成参数与密钥引用，不代理请求，也不产生唤醒。

castworks 把事件源作为独立模块：LLM 网关代理模型调用并记录在途请求，连接器处理 webhook 与状态式轮询并登记订阅，人类通道把聊天、即时通讯与 Issue 评论转为收件箱事件。三者经统一汇入契约写入控制面。

## Agent 协作模型差异

| 方面 | AX | castworks |
| --- | --- | --- |
| 与 Agent 的关系 | runner 契约规定容器内启动、监督、探针、元数据与关闭；不解释 Agent 的回合 | Agent 驱动器把 Agent 原生信号翻译为协议事件，把投递翻译为原生输入 |
| 协作层级 | 没有分层；任何能被容器启动的 Agent 都使用同一契约 | L0 纯观测、L1 驱动器中介、L2 协作式，按可观测信号与挂起机制分层 |
| 回合边界 | 不建模；命令退出后 runner 继续存活，控制面不读取命令退出状态 | 对 L1 与 L2 而言，这是唯一允许以挂起为目的销毁沙箱的时点，以 `idle` 与 `result` 判定；销毁只在回合边界上无在途请求等 I9 条件同时满足的安全点执行 |
| 续接 | 恢复后重新启动命令 | L1 以 Agent 自身的会话恢复机制续接；恢复句柄在销毁前落库 |
| 等待声明 | 无 | L2 经 `WaitDeclared` 追加显式条件，L1 的等待由驱动器边界信号推导 |

AX 的 Claude Code 集成以无头单次会话运行，配置经 `spec.config` 透传为命令行参数。这是可配置的启动方式，不是回合级协作协议。

## 安全边界的设计取向

| 方面 | AX | castworks |
| --- | --- | --- |
| 密钥位置 | 任务的环境变量；文档示例把模型提供方密钥作为 `spec.env` 传入 | 只在托管侧进程内存与密钥库中出现；沙箱内只有运行实例令牌 |
| Agent 权限 | 沙箱内进程以 root 身份运行，并可绕过权限确认；隔离由沙箱承担 | Agent 以每运行实例 uid 运行，`no_new_privs`，清空 capability bounding set |
| 网络出口 | AX 的资源模型未定义出口策略 | 出口代理默认拒绝，按每运行实例的出口策略放行，凭据以占位符替换 |
| 身份 | 资源按 atespace 组织，atespace 不是租户隔离边界 | 运行实例令牌绑定代，LLM 网关与连接器换取凭据时校验代 |

两端都把沙箱作为主要隔离手段，但对「沙箱内能拿到什么」的约束相反。castworks 的设计不变量 I6 要求沙箱内不持有任何长期凭据与 LLM 密钥；AX 的设计让密钥随任务环境进入沙箱。

## 一致性与错误处理差异

| 方面 | AX | castworks |
| --- | --- | --- |
| 状态事实源 | 资源规格与 AX 自身工作状态存 PostgreSQL；actor 的运行状态从 Substrate 读取 | 运行实例状态、收件箱、等待、订阅、定时器与租约只存 PostgreSQL |
| 并发控制 | 每资源的分布式租约锁，等待者轮询 | 运行实例行锁、所有者租约与 `owner_epoch`、工作区租约 |
| 过期动作 | 没有运行实例级失效判定；任务创建后不可变 | 代单调递增；消息、令牌、工作区写入与游标按代校验 |
| 投递语义 | 不定义事件投递 | 至少一次投递，`Accepted` 与 `Consumed` 两级确认，投递意图日志随工作区持久化 |
| 错误恢复 | 以 phase 与 condition 表达；失败动作可重试 | 过渡态带截止时间，纠正性对账器按持久化状态幂等重驱动 |

## 环境供给与编排能力差异

AX 的编排能力更完整：`Task` 是不可变、创建后不可修改的执行声明；`Workspace` 是可复用的环境模板，声明 git 仓库、内联文件、MCP 服务器与 skills；`Model` 是可复用的模型配置；资源按 atespace 组织；CLI 采用 kubectl 风格的 `apply`、`get`、`describe`。

castworks 的设计以运行实例为中心：工作区由控制面绑定并带租约，环境供给分散在工作区绑定与看守进程的首次准备中，没有可复用的环境模板资源，也没有声明式 CLI。控制面接口是 `Create`、`End`、`SetRunFact` 与 `AdmissionState` 这类命令式方法。

这一维度的方向与前几项相反：AX 覆盖 castworks 的比例低，castworks 覆盖 AX 的比例也低，两端各自缺少对方的一半。

## 术语对照

AX 与 castworks 使用若干同形词，含义不同。按同形词计分会系统性高估重合度。

| AX 术语 | castworks 术语 | 关系 |
| --- | --- | --- |
| `Task` | 运行实例 | 不同：AX 是不可变的声明式执行资源，castworks 是跨多代沙箱存活的执行实体 |
| `Workspace` | 工作区 | 不同：AX 是可复用的环境模板，castworks 是每运行实例的持久化目录 |
| `Model` | LLM 网关与密钥库 | 部分：AX 只描述模型提供方与密钥引用，castworks 代理请求、换取凭据并跟踪在途请求 |
| atespace | 项目与租户维度 | 部分：AX 是扁平命名空间，castworks 是数据模型维度 |
| suspend / resume | 挂起 / 恢复 | 不同：AX 是快照加暂停，castworks 是冻结、快照与销毁重建的统称 |
| actor | 沙箱 | 近似：AX 的 actor 是 Substrate 的执行单元，castworks 的沙箱是隔离计算实例 |
