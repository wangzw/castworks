# 技术验证

本文记录设计依赖、但尚未经实测确认的外部行为，每项结果决定的参数或路径，以及已有的验证结论。它位于设计规范管辖的目录之外，不受设计文档章节结构的约束。设计结论以 [架构](../design/architecture.md) 与 [ADR](../adr/README.md) 为准；验证结果改变参数或机制选择时，修改对应设计文档与 ADR，本文不复制状态机、协议与参数定义。各版本覆盖哪些验证项，见[里程碑](README.md)。

技术验证清单中的“通过”表示可观察条件成立，“不通过”表示按对应回退路径处理。

## 当前验证结论

原有结论的验证环境为 macOS arm64、Docker Desktop Linux 容器（cgroup v2）、Kubernetes 1.36.4 与 Claude Code 2.1.318。2026-11-19 的 Substrate 结论在开发集群上实测：单节点 Kubernetes 1.37.2、arm64、Substrate v1.0.0、gVisor（release-20261102.0，systrap）、Claude Code 2.1.328；actor 镜像为 `registry.zhanwei.wang/castworks/actor@sha256:8347ea189ec39bf58d9ceec7b788f3a67431fe62b9b25e8df89ee54f4dd2ff5c`，来源提交记为 `430f63a`：这个值取自 `measurements.json` 的 `repo_commit` 字段，该字段是操作者经 `ACTOR_COMMIT` 环境变量传入的，没有独立的构建记录。控制面与看守进程代码与提交 `0add82d` 相同；当时的验收代码还没有 `hello_at` 放宽，`hello_ms` 为空的挂起记录按失败计，判定比现在更严。`430f63a` 之后看守进程自身的生产代码只有 `819141d` 一处改动：`internal/warden/claudecode/stream.go` 增加 3 行，把 `rate_limit_event` 按信息类消息处理，不再落入未知消息分支。同一区间里 `internal/agentprotocol` 的改动只涉及控制面调用的 `ValidateWardenFrame`，看守进程调用的是 `ValidateControlFrame`，没有改动，所以镜像与验收时代码的看守进程行为相同，只差这条日志的级别。已采集的日志中 `ignored stdout message` WARN 出现 3 次，类型都是 `rate_limit_event`，原因就是镜像尚未包含这条改动；行为不受影响，没有重建镜像。这些结论不是目标环境验收，k8s 提供者路径尚未在目标集群做端到端实测。下表的“通过”表示机制、官方文档与实测相互印证。

## 冷启动两个样本的条件

两次运行都在同一个单节点集群上，atelet 与 worker 池相同。第一个样本（`/tmp/castworks-acceptance/20261119T200221Z`）对应镜像在该节点上的第一次拉取，第二个样本（`/tmp/castworks-acceptance/20261119T234232Z`）在约 3 h 40 min 之后。

镜像层缓存。依据是开发集群节点上的 atelet 日志：Pod `ate-system/atelet-9ljvp`，容器 `atelet`，镜像 `ghcr.io/agent-substrate/substrate/atelet:v1.0.0@sha256:79abc69f982392adbcbc3332cd8191cf74ac3cd1f4a43c44e9c8a3ce16488b6e`。两个样本的日志摘录分别存档在 `/tmp/castworks-acceptance/20261119T200221Z/atelet-excerpt.log` 与 `/tmp/castworks-acceptance/20261119T234232Z/atelet-excerpt.log`，汇总在 `/tmp/castworks-scratch/closeout-fix2-evidence/summary.json`，原始日志在 `/tmp/castworks-scratch/closeout-fix2-evidence/atelet-raw-1955Z.log`。第一个样本在 20:02:28.728 记录 `Image cache miss`，随后在 20:02:43.510 记录 `Image pulled into layer cache`，共 10 层，耗时 14.78 s；同一次 `Atelet/Run` 的 elapsed-time 为 14.97 s。第二个样本在 23:42:39.506 记录 `Image cache hit`，同一次 `Atelet/Run` 的 elapsed-time 为 198 ms。worker Pod 中没有名为 `atelet` 的容器，worker 侧的容器日志取不到，出处为上述节点级 atelet 日志。控制面的 provision 耗时分别是 15036 ms 与 250 ms，与 atelet 的两次 Run 对应；15036 ms 与 250 ms 的差就是首次拉取镜像的代价。

actor 模板。`kubectl ate get actor-template -a castworks-dev -o json` 的实测记录存档在 `/tmp/castworks-acceptance/20261119T200221Z/agent-template-createTime.txt` 与 `/tmp/castworks-acceptance/20261119T234232Z/agent-template-createTime.txt`，汇总见 `/tmp/castworks-scratch/closeout-fix2-evidence/summary.json`。第一个样本的控制面日志在 20:02:28.648 有 `created actor template`（`castworks-dev/cw-8347ea189ec3`），模板的 `createTime` 实测为 2026-11-19T20:02:28.643163691Z；第二个样本的控制面日志没有这一行，模板已存在约 3 h 40 min，复用了同一个模板，其 `createTime` 与 `goldenSnapshotConfig.mode` 与第一个样本相同。模板创建发生在 provision 之前，不构成那 15 s 的耗时，但它是两个样本在集群状态上的另一处差别。

worker。两个样本使用的 worker Pod 都已运行数小时：第一个样本是 `castworks-767b6ff54c-fcm2n`（创建于 2026-11-19T14:08:01Z），第二个样本是 `castworks-767b6ff54c-fvl7t`（创建于 2026-11-19T15:02:18Z）；两个时刻取自 Pod 的 `metadata.creationTimestamp` 与 ate-controller 的注册日志，汇总在 `/tmp/castworks-scratch/closeout-fix2-evidence/summary.json`，控制器日志在 `/tmp/castworks-scratch/closeout-fix2-evidence/ate-controller-full.log`。两次都不是刚启动的 worker。v0.1.0 在 actor 模板中关闭了模板快照（`goldenSnapshotConfig.mode` 为 `GOLDEN_SNAPSHOT_MODE_DISABLED`，实测记录见上面两个 `agent-template-createTime.txt`），没有预热池，actor 每次都冷启动，镜像层缓存之外没有可复用的启动状态。

第一个样本的验收运行本身在清理步骤失败（`kubectl ate get actor -o name` 不受支持），冷启动测量在此之前已完成并写入 `coldstart.json`；该样本的数值只用于冷启动，不作为通过标准的依据。

## Substrate 试点的 go 判定

Substrate 试点的 go 判定如下，全部满足为 go：

| 判定项 | 可观察条件 |
| --- | --- |
| 驱动 Claude Code | 看守进程以 PID 1 在 gVisor 下驱动 Claude Code 完成一个回合：启动、LLM 请求、工具调用与回合结束均可观察，进程树受看守进程监督 |
| 快照恢复 | 约 500 MiB actor 的 Suspend 与 Resume 时延与快照大小可重复测量；快照恢复 p95 < 5 s，或偏差可归因于已知项并触发目标调整 |
| 入站唤醒 | 经带 `ate-target-actor: <atespace>/<actor>` 头的路由器调用 `/wake` 成功唤醒；控制面以 SPIFFE 身份（[REF-spiffe](../references.md)）通过白名单；`parked-request-budget` 只约束新的恢复重试，客户端被持有的上限是预算加 5 s，部署同时设置 `drain-timeout` 与 `terminationGracePeriodSeconds` |
| 网络前提 | actor 内 uid 非 0 的出站只到回环；对离开内部网络的目的地，非 TCP 出站除 DNS 查询外不可用，UDP 静默丢弃，其他非 TCP/UDP 以 ICMP unreachable 拒绝；DNS 中继只应答 EgressPolicy 所列主机与控制面主机，其余返回 NXDOMAIN 且不递归，查询名不出沙箱；actor 网络为 IPv4-only |
| 出口网关请求层一致性与 CA 轮换 | `https` 规则在连接层要求 SNI 匹配、请求层要求 `Host` 等于 `:authority`；`tls_passthrough` 规则要求 SNI 等于规则主机并显式列端口；ECH 的处理按实测结论；拒绝以 `atenet.router.route.duration{outcome=denied}` 观测；CA 轮换重叠期不短于快照保留期上限 |
| 出口策略 | EgressPolicy 对 `api.github.com` 与 git 的占位符注入生效，缺头不注入，未列主机默认拒绝；S3 插件可用 |
| 引导领取 | 出口网关为看守进程发往引导接口、携带 `Authorization` 占位符的请求注入 audience 为 `castworks-bootstrap` 的 actor JWT，引导接口经 Substrate 签发方的 OIDC 发现验签、核对 actor 名与 actor UID 后返回运行实例令牌与 `lease_id`；首代从模板快照恢复的 actor 在 `wakeupProbe` 探测时读到新的 `actor-name` 并立即领取，actor 处于 `RESUMING` 时出口已放行，领取可以在 `ResumeActor` 返回之前成功；同一代内的再次领取返回 409；同一 actor 冷启动为新一代之后，看守进程按新一代的引导记录领取成功 |
| 按代冷启动 | actor 处于 `SUSPENDED` 时改挂另一个模板槽位，下一次 `ResumeActor` 是冷启动：新的看守进程从头启动、领取并以 `claude -p --resume` 续接上一代的会话；冷启动之后的快照仍为 MEMORY 保真度；actor 崩溃或看守进程退出之后，经 `RevertActor` 与槽位切换能再次冷启动；冷启动加 `--resume` 的时延可重复测量 |
| 工作区持久化 | 外部 CSI 卷（NFS CSI 驱动）在 actor 内可挂载，Agent 的运行实例 uid 可写；卷内容在挂起、`RevertActor`、崩溃与冷启动之后保留，只随 `DeleteActor` 删除；actor 存在期间沙箱外可经同一导出读取。不可用时 `durableDir` 在同一 actor 冷启动之后恢复为最近一次挂起时的内容，同步挂起的耗时与崩溃丢失窗口可测并落在可接受范围 |
| 恢复后状态 | MEMORY 快照恢复后客户机时钟可按服务端时刻校正，看守进程的工作区租约续约在校时之后成功，之后出站流重建、`Hello` 被接受；旧 TCP 连接可被察觉并断开，本地代理按 `request_id` 取回在途请求的已完成响应 |
| 负载兼容 | 编译测试类负载在 gVisor 下的开销与无 Docker 的影响可度量，不阻断 Claude Code 驱动 |

任一判定项不成立且无补偿路径为 no-go。no-go 时 Substrate 路径不上线；能力分层、策略只在能力集内选择机制，这一设计不变（[ADR-capability-tiered-suspension](../adr/adr-capability-tiered-suspension.md)）。
