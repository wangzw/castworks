# 出站流只重放看守进程发出的消息，控制面发出的消息按持久化状态重新产生

## 背景

[出站流](../glossary.md)是[看守进程](../glossary.md)主动连向控制面的 gRPC 双向流，会断开并重建；同一条连接内传输有序，跨连接没有任何保证。两个端点在重连前后的处境不同。

看守进程一端：看守进程是[沙箱](../glossary.md)的 PID 1，崩溃即沙箱丢失，不就地重启（[ADR-warden-is-pid1](adr-warden-is-pid1.md)）。同一[代](../glossary.md)内重连的始终是同一个看守进程，它的内存在两条连接之间保持不变。

控制面一端：出站流终止在接受 `Hello` 的副本上，重连时 `Hello` 可能到达另一个副本，接收副本在同一事务接管[运行实例](../glossary.md)的所有权（[ADR-single-writer-per-run](adr-single-writer-per-run.md)）。上一个副本内存中的状态不随所有权转移。

控制面发往看守进程的消息由 `runcontroller` 的状态机产生，产生依据是持久化状态：未被 `Accepted` 的投递批、未终结的挂起尝试、沙箱侧配置的修订号、最近签发的令牌组等。`Hello` 携带看守进程一侧的状态摘要，包括 Agent 进程的阶段、已应用的沙箱侧配置修订号与所持令牌的到期时刻。两个方向的重复效果由应用层幂等标识吸收，例如 `delivery_id`、`suspend_id`、`freeze_id`、`exec_id` 与 `revision`。

下文的应用消息指出站流上除握手、关闭、确认与遥测之外的消息。

## 考虑过的选项

### 两个方向对称地跨连接重放

采用它意味着两端各自在内存中保留未确认的应用消息，重连后按对端确认的位置重放；控制面副本切换时，新所有者以持久化的流状态继续发往看守进程的序号，旧副本未确认的消息由状态机按持久化状态重新产生。**否决**：控制面一端的重放缓冲在所有者切换时丢失，状态机按持久化状态重新产生消息的规则无论如何都要有；同一条消息于是有两条补发路径，同一副本内靠重放，跨副本靠重新产生，两者的结果须保持一致。看守进程还要为控制面的消息维护跨连接的去重表与乱序缓存。

### 持久化发往看守进程的序号与未确认消息

采用它意味着控制面把每条发往看守进程的应用消息连同序号写入数据库，重连或所有者切换后从数据库按序重放。**否决**：每条发往看守进程的消息都在发送路径上多一次数据库写入。重放出的是发送时刻的内容，重连后真正需要的消息却取决于当前持久化状态与 `Hello` 的状态摘要：是否重发 `StartAgent` 取决于 Agent 进程所处的阶段，是否重发 `TokenRotate` 取决于看守进程所持令牌的到期时刻，是否重发 `SandboxConfig` 取决于修订号比较。按存档重放会送出已经过时的消息，看守进程仍要靠幂等标识丢弃它们。

### 看守进程发出的消息跨连接重放，控制面发出的消息按连接编号、按持久化状态重新产生

采用它意味着看守进程在内存中保留自己发出的未提交消息，控制面把已提交的位置随消息处理一起持久化；控制面发出的消息只在一条连接内有序，连接断开即作废，由状态机在下一次接受 `Hello` 时按持久化状态重新产生。**采纳**，见决策。

## 决策

采用按方向不对称的跨连接可靠性：

- 看守进程发往控制面的应用消息，序号作用域为 `(run_id, generation)`，本代内从 1 起严格递增、跨连接连续。看守进程在内存中保留重放缓冲；控制面把已提交的序号写入 `run.in_msg_seq`，与该消息的处理事务同事务提交。重连后 `HelloAck` 返回这一位置，看守进程据此裁剪缓冲，从其后按原序号、原内容重放。
- 控制面发往看守进程的应用消息，序号作用域为一条已接受的连接，每次接受 `Hello` 后从 1 编号。控制面不保留跨连接的重放缓冲，不持久化这一方向的序号；连接断开时未确认的消息作废。每次接受同代 `Hello` 时，`runcontroller` 按持久化状态与 `Hello` 的状态摘要重新产生仍然需要的消息。
- 两个方向的接收方都串行处理：前一条的处理事务提交之后才派发下一条。传输有序，重放又从已提交的位置之后开始，序号出现缺口只能来自实现缺陷，按协议违规处理（[ADR-unrecoverable-stream-failure-rebuilds-sandbox](adr-unrecoverable-stream-failure-rebuilds-sandbox.md)）。

## 后果

本决策使项目承担以下义务，穷举如下：

- `runcontroller` 为每一种发往看守进程的应用消息规定重新产生的规则，规则清单是穷举的；新增这一方向的消息种类必须同时给出规则。
- 每一种发往看守进程的应用消息都必须带应用层幂等标识，或重复执行不改变结果；`ToolExecRequest` 按 `exec_id` 幂等，重复的请求附着到进行中的执行或重发已记录的结果。
- 看守进程在每条新连接上把控制面消息的接收位置重置为 0，丢弃上一条连接的接收状态。
- 看守进程在发送 `Hello` 之前，让上一条连接上正在处理的控制面消息处理完或中止，使 `Hello` 的状态摘要反映它；控制面对 `Hello` 与消息处理都取运行实例行锁。
- 看守进程处理控制面消息失败时不确认，断开后重连，由控制面在下一次接受 `Hello` 时重新产生该消息。
- 代变化时两个方向的缓冲与接收位置全部丢弃，序号从 1 重新开始。

承担的代价穷举如下：

- 每次重连，控制面都会重发它判定仍然需要的消息，包括看守进程在上一条连接上已经收到的；看守进程依靠幂等标识丢弃重复，重连越频繁，重复的消息与处理越多。
- 重新产生的规则漏掉某种情形时，对应的消息在重连后丢失，只能等过渡态截止时间与对账器纠正（[ADR-state-based-reconciliation](adr-state-based-reconciliation.md)）。
- 看守进程一侧的重放缓冲只在内存中，未确认消息的条数与字节数有上限（`W_replay_msgs`、`W_replay_bytes`）。出站流长时间不可用时，新产生的消息进入看守进程的待发队列，队列达到 `Q_pending_bytes` 时看守进程冻结 Agent 进程树。
- 每个方向同一时刻只有一条消息在处理，单个运行实例的消息吞吐受处理事务时延限制。

## 失效条件

- 出现某种控制面发往看守进程的消息，其内容不能由持久化状态与 `Hello` 的状态摘要确定，按状态重新产生对它不可行。
