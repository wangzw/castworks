# 每运行实例单写者与汇入例外

## 背景

控制面由多个副本组成，运行实例的状态转移、协议消息、定时器触发、效果执行与对账可以落到任一副本。沙箱的出站流终止在接受 `Hello` 的副本上，活动度摘要与恢复准入队列只存在于该副本的内存中。事件源模块（LLM 网关、连接器、人类通道）并发写入同一运行实例的事件与事实，写入者之间不协调顺序。

状态机的正确性要求同一运行实例的转移串行化：挂起决策、唤醒、投递确认与代递增不能基于过期的状态交错执行。副本会崩溃，运行实例在挂起态也可能没有存活的沙箱与控制面连接，唤醒仍然必须能够发生。控制面数据库提供行锁与唯一索引，不提供跨副本的领导者选举或分布式事务。

## 考虑过的选项

### 按 `run_id` 静态分片到副本

采用它意味着每个运行实例固定归属于一个副本，由成员管理与再平衡决定归属，其他副本把该运行实例的请求转发过去，状态转移只由归属副本执行。**被拒**：归属本身是分布式分配问题，需要成员协议、再平衡与故障检测；副本故障时仍要租约或共识来决定新归属；事件源必须知道归属并转发，新增事件源与事件源故障都变得更复杂；挂起态运行实例没有存活的沙箱连接，归属副本失效后无人唤醒它。

### 所有副本都可写，只靠数据库行锁串行

采用它意味着任一副本都可以处理任一运行实例的消息与转移，`run` 行锁保证同一时刻只有一个事务在写，不引入所有权概念。**被拒**：行锁能串行化写入，但不能决定哪个副本持有该运行实例的出站流与内存中的活动度、准入队列；一个没有出站流的副本可能依据过期的活动度做出挂起决策，效果也找不到目标流；副本崩溃后，内存状态的归属无从判定，协议消息可能由没有上下文的副本处理。

### 全部写入经单一主副本或共识

采用它意味着所有运行实例的写入都经过一个主副本，或每次转移都经共识提交。**被拒**：吞吐与可用性压在单点；每次转移多一段共识时延；主副本故障期间整个控制面不可写；与 PostgreSQL 已提供的行锁和唯一索引相比，引入新的复制与故障恢复机制。

### 所有者租约、`owner_epoch` 与汇入例外

采用它意味着每个运行实例有一个所有者租约，任一时刻只有一个副本持有有效租约并执行状态转移；`Hello` 的接收副本通过同一行锁接管所有权，效果执行器、定时器扫描与对账器可以认领过期租约；事件源模块只经汇入契约写入，汇入事务（含 `runcontroller` 自身的内部汇入路径）由任一副本执行、不校验所有权，是唯一由非所有者推进运行实例状态转移的写事务，只执行 `Suspended` 转 `WakeQueued` 一条条件 UPDATE；所有权获取事务建立所有权而不校验既有的 `owner_id` 与 `owner_epoch`；清理任务的删除只删除过期行，不改变运行实例状态。**采用**——见决策。

## 决策

采用每运行实例单写者：任一时刻只有一个控制面副本是某个运行实例状态机的写者，由 `run` 行的所有者租约与 `owner_epoch` 决定；事件源模块只经汇入契约写入，汇入事务（含 `runcontroller` 自身的内部汇入路径）由任一副本执行、不校验所有权，是唯一由非所有者推进运行实例状态转移的写事务，只执行 `Suspended` 转 `WakeQueued` 一条条件 UPDATE；所有权获取事务建立所有权而不校验既有的 `owner_id` 与 `owner_epoch`；清理任务的删除只删除过期行，不改变运行实例状态。

## 后果

本决策使项目承担以下义务（穷举）：

- 每个所有者事务在 `run` 行锁内先校验 `owner_id`、`owner_epoch` 与租约未过期；校验失败即回滚、丢弃该运行实例的内存状态并关闭出站流。
- 通过 `Hello` 公共校验的接收副本在同一事务接管所有权，`owner_epoch` 加一、`owner_id` 改为自身；未通过校验的 `Hello` 只应答，不改变所有权。
- 所有者租约过期后的运行实例由效果执行器、定时器扫描或对账器以条件 UPDATE 认领；受理 `Create` 的副本成为首个所有者。
- 所有者对有出站流、处于过渡态或 `WakeQueued`、或有 pending 效果记录的运行实例批量续租；其余运行实例的租约允许过期。
- 与数据库分区的副本以本地单调时钟判定续租超时，超时后关闭出站流并丢弃内存状态，不得在新所有者接管之后继续持流。
- 汇入事务不校验所有权；除决策所述的条件 UPDATE 外，只写入收件箱（含 `run` 行上的收件箱最大序号）、唤醒信号、运行实例事实与事件源实例租约，并在产生需所有者处理的变化时写入通知所有者的效果记录。
- 事件源模块只经汇入契约写入；汇入写入集合、通知所有者的效果记录的写入条件与汇入契约的稳定性承诺不在本记录重述。
- 活动度摘要、恢复准入队列与其他只在所有者内存中的状态，在所有权转移后必须能从 `run` 行重建；无法重建的活动度摘要按零累计处理，新所有者累计不足静默判定所需时长时，静默检查与空闲证据判为不成立；恢复准入队列必须按 `run` 行重建，不得以「不足即不成立」丢弃条目。

承担的代价穷举如下：

- 同一运行实例的全部状态转移被一个 `run` 行锁串行化，单运行实例的吞吐上限由该行锁决定。
- 所有者故障切换最长一个租约周期不可写；切换期间汇入继续写入，但状态转移要等新所有者接管。
- 汇入事务与所有者事务争同一行锁，单运行实例的事件风暴会让控制面数据库成为唤醒延迟的关键路径。
- 所有者是该运行实例出站流与内存状态的单点；所有者副本过载会影响该运行实例的全部交互。
- 汇入契约、所有者事务、所有权获取与清理删除等多条写入路径并存，`owner_epoch` 校验与内存状态重建增加实现与排障成本。

## 失效条件

- 同一运行实例的事件写入因行锁串行化持续达不到解冻路径的时延目标，且合并写入不能消除该排队。
- 控制面数据库提供原生的跨副本所有权与领导者选举，且其切换时延与成本低于当前租约机制。
- 单个所有者副本无法再容纳某运行实例的活动度与准入队列，需要把内存状态外置。
