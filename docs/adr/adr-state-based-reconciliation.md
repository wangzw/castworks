# 以持久化状态与纠正性对账收敛

## 背景

运行实例的状态分散在控制面数据库、沙箱提供者、工作区与看守进程中。一次转移可能包含多次外部调用与多个数据库事务；副本可能在任何一步崩溃，消息可能丢失，提供者可能超时或返回不确定结果。系统不能依赖所有参与方同时可用，也不能要求外部系统支持分布式事务。

运行实例必须能在没有人工介入的情况下从这些中断中恢复；恢复的依据必须是控制面能够读取并核验的持久化事实，而不是可能丢失或乱序的事件历史。部分状态无法自动纠正时，系统必须识别并告警，而不是静默停留。

## 考虑过的选项

### 重放事件历史

采用它意味着控制面保存全部事件，恢复时按事件顺序重放，由此重建运行实例状态。**被拒**：历史随运行实例增长且没有自然上界；外部副作用不可重放，重放会产生重复调用；沙箱提供者、工作区与看守进程的实际状态不在事件日志里，重放不能恢复它们；消息乱序与丢失本身就会使重放结果不确定。

### 为每次转移编写补偿事务

采用它意味着每次状态转移都配一个逆向操作，失败时逐步回滚已经完成的部分。**被拒**：沙箱提供者、工作区与 `secrets` 不提供可逆操作；补偿逻辑与转移逻辑一一对应，数量随转移表增长；消息丢失或副本崩溃仍需要额外的对账来发现未完成的转移。

### 只告警、人工修复

采用它意味着系统只检测异常并发出告警，由运维人员判断与恢复。**被拒**：停住的过渡态没有就地修复的运维动作，只能由对账器自动纠正，或以结束运行实例收场；故障期间运行实例一直不可用，不符合恢复时延目标；告警数量随运行实例规模增长，人工处理不可扩展。

### 持久化状态、截止时间与纠正性对账

采用它意味着每个过渡态带截止时间与幂等标识，控制面以持久化状态为准周期扫描，对停住的运行实例以同一标识重驱动；出站流断连后以状态对账恢复一致；告警只针对对账器纠正不了的状态。**采用**，见决策。

## 决策

采用以持久化状态为准的纠正模型：每个过渡态带截止时间与幂等标识；对账器按周期扫描持久化状态，对停住的运行实例以同一标识幂等重驱动。出站流断连后以 `Hello` 与 `HelloAck` 做状态对账，不重放事件历史（I10）；告警只针对对账器纠正不了的状态。

## 后果

本决策使项目承担以下义务，穷举如下：

- 每个过渡态必须有截止时间，每个重驱动必须使用同一幂等标识，使沙箱提供者与看守进程能返回首次结果。
- 对账器的守卫必须是闭集，且以持久化状态为事实源；外部系统的实际状态只由有限的外部查询核验，外部事件订阅只用于生成候选或触发评估，不构成判定证据。所有者内存中的准入队列是缓存，只用于核对 `wake_queued` 条目是否缺失，不作为判定证据；守卫不得依赖事件历史。
- 对账器只做纠正，不作为告警源；同一运行实例的同一守卫连续纠正达到阈值后仍命中时才告警，且不得伪造状态转移。
- 外部查询失败时，该周期不得据此判定；查询结果必须在事务内与 `run` 行核对。
- 出站流重连必须用状态对账补偿丢失的消息与确认，不能用重放事件历史代替状态对账。
- 纠正性动作必须幂等，且不得覆盖在线转移已经提交的结果。

承担的代价穷举如下：

- 对账器常驻扫描带来持续的数据库负载与部分索引维护成本。
- 纠正时延至少为一个对账周期；对账周期与截止时间的取值需要在时延与负载之间权衡。
- 每个过渡态都要有截止时间、守卫与幂等标识，状态机与效果类别的实现负担增加。
- 守卫误判会触发一次不必要的沙箱重建或其他纠正动作。
- 对账器不能消除告警，只能把可自动纠正的偏差从告警范围中移出。

## 失效条件

- 外部系统提供可原子提交且可查询的分布式事务，使跨系统状态不再需要纠正性对账。
- 出现无法从持久化状态判定的过渡态，且其纠正必须依赖事件历史。
