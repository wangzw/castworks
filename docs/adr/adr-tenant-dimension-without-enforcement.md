# 保留租户维度而不实现跨租户隔离

## 背景

平台面向单组织内部使用：运行实例、工作区、预热池与配额记录只属于一个组织，不存在多个组织同时使用同一控制面的场景。数据模型需要为多租户预留租户维度（`tenant`）：运行实例与工作区一旦缺少租户归属，接入第二个组织时无法把既有记录划归到任一组织，也无法按组织核算资源。跨租户配额与抢占依赖多租户负载下的调度验证：配额核算、抢占优先级与组织间公平性的正确性只有在多个组织竞争同一容量池时才可观测。本决策只涉及数据模型与配额、抢占之间的取舍，不涉及表结构。

## 考虑过的选项

### 完全不建模租户

数据模型不携带租户维度，运行实例、工作区、预热池与配额记录处于同一命名空间，资源归属只由运行实例标识表达。**被拒**：接入第二个组织时，既有记录没有可用于划分归属的字段，迁移需要为每条记录重新确定组织，且无法从历史数据推导；单组织取值下新增该字段只影响写入路径，事后迁移则需要逐条重建归属。

### 实现完整多租户隔离、配额与抢占

数据模型、鉴权、调度与预热池全部按租户分片；控制面维护租户配额账本，跨租户抢占与公平调度成为该方案必须交付的能力；每个租户拥有独立的预热池与挂载根。**被拒**：平台面向单组织内部使用，跨租户隔离不解决任何实际存在的资源竞争或越权；配额与抢占的调度正确性依赖多租户负载，在单组织负载下无法验证；这些能力把调度器、配额账本与预热池分片扩展为该方案必须维护的组件，而单组织负载下没有第二方参与竞争。

### 保留租户维度而不实现隔离

数据模型携带租户维度，当前只有单组织取值；跨租户配额与抢占不实现，预热池与挂载根由该组织共享。**采用** — 见决策。

## 决策

采用保留租户维度而不实现跨租户隔离的方案：数据模型保留租户维度（`tenant`），不实现跨租户配额与抢占，预热池与挂载根为单组织共享。

## 后果

本决策使项目承担以下义务（穷举）：

- 数据模型中的所有运行实例、工作区与配额记录必须保留租户维度，即使当前只有单组织取值。
- 跨租户配额与抢占不在当前实现范围内；容量规划按单组织总量计算，无法按组织分配或回收资源。
- 预热池与挂载根为单组织共享，平台机制不处理组织间的资源竞争与数据越权；接入第二个组织前必须补充隔离、配额与抢占能力。

承担的代价穷举如下：

- 租户维度的传递与维护在当前只有一个取值，其成本不对应任何跨租户行为。
- 租户维度不构成安全边界；第二个组织接入时不能仅凭该维度完成隔离。
- 配额与抢占能力缺失，当前实现无法限制单个组织的资源占用，也无法在容量不足时按优先级回收。

## 失效条件

- 出现第二个组织要求独立资源配额、调度优先级或数据边界的接入需求。
- 单组织负载下实测出现一个工作负载持续占用容量并延长其他运行实例的恢复时延，且按组织限额可以消除该影响。
- 数据模型中出现必须写入不同租户取值的代码路径，单一取值不再成立。
