# 投递幂等状态随工作区持久化

## 背景

事件投递的语义是至少一次：出站流会断连，看守进程会崩溃，沙箱会在代之间销毁重建，控制面副本会切换，因此投递与确认消息可以丢失，同一事件可能被重复投递。收件箱中的事件包含人类消息、外部系统事件、审批决定与内部通知（为举例）；重复投递会使 Agent 重复执行工具调用或重复回复人类。

运行实例跨越多代沙箱。销毁重建后 Agent 以自身会话恢复机制续接，Agent 进程的内存状态不跨代保留，工作区是跨代保留的可写状态。控制面数据库中的投递游标只反映控制面何时发送事件与何时收到确认，不反映 Agent 何时开始处理事件；确认丢失、看守进程在缓冲事件后崩溃，或沙箱在下一回合开始前被销毁时，控制面无法据此判断事件是否需要重新投喂。看守进程在代内知道自己写入过哪些投递，其内存同样不跨代保留。

事件是否已被 Agent 处理，这一事实必须有一个跨代可读的记录，判定才不会在每一代重新回到不确定。

## 考虑过的选项

### 只在控制面内存或数据库中去重

采用该选项意味着：控制面以 `(run_id, dedup_key)` 维护已投递集合，内存缓存由控制面副本持有，持久形态由控制面数据库承担；沙箱不保存投递状态。

**被拒**：控制面能够记录自己何时发送，不能记录 Agent 何时消费。确认在途丢失或沙箱在消费前被销毁时，控制面只能选择重投（Agent 已处理则重复）或不再投递（Agent 未处理则丢失），至少一次语义无法成立。把确认窗口缩到最小并不能消除该窗口，数据库中的投递记录与 Agent 的实际处理之间没有共同的观察点。

### 单级确认，收到即视为已消费

采用该选项意味着：看守进程收到 `Deliver` 即返回确认，控制面随后推进投递游标，该事件不再投递。

**被拒**：确认发生在事件进入看守进程的缓冲区时，尚未成为 Agent 的输入。看守进程在确认后崩溃，或 Agent 在开始处理前被销毁，事件既不重投也不被处理，至少一次退化为至多一次。单级确认也无法为重建后的重新投喂提供判定依据。

### 投递意图日志随工作区持久化

采用该选项意味着：看守进程在把事件交给 Agent 之前，先在工作区内追加记录并把记录同步到持久存储；在观察到 Agent 开始对应回合后追加消费记录。重建后的看守进程按日志判定哪些事件已交给 Agent、哪些已消费，不确定时带重新投递标记重喂。确认分为 `Accepted` 与 `Consumed` 两级，分别表示事件已成为 Agent 的输入与 Agent 已开始处理。

**采用** — 见决策。

## 决策

采用工作区内的投递意图日志承载投递幂等状态，该状态跨代有效；投递确认分 `Accepted` 与 `Consumed` 两级。

## 后果

投递的重复判定在代之间保持一致，重建后的看守进程按工作区日志自行判定，不需要从控制面重建去重状态。

本决策使项目承担以下义务（穷举）：

- 看守进程在把事件交给 Agent 之前完成投递意图日志的同步写入；写入失败时不得把事件交给 Agent。
- 事件的重新投递由日志驱动，并携带重新投递标记，使 Agent 侧可以识别可能重复的输入。
- 工作区布局必须为平台状态留出位置，日志与 Agent 自身状态一同保留；工作区清理、配额与快照策略不得把日志排除在持久化范围之外。
- 各沙箱提供者的工作区实现都必须提供同步写入的持久化语义；持久化确认的差异由工作区模块承担。
- 控制面游标与日志记录并存，控制面的确认消息必须能区分两级状态，对账器需要容忍已接受但未消费的事件。

承担的代价穷举如下：

- 投递路径增加工作区同步写入：每次投递写入接受记录，每次回合开始写入消费记录；投递路径的延迟下界由工作区同步写入的时延决定。
- 正确性依赖工作区的持久化保证。退化配置下工作区写入可能在上次快照之后丢失，日志与事件输入一同丢失，此时只能依靠重新投递与 Agent 侧的幂等承受重复。
- 投递幂等状态不能由控制面单独查询。判断某事件是否已消费需要读取工作区，运维与排障因此依赖看守进程或其上层接口。
- 已接受未消费的窗口是常态而非故障，对账逻辑与告警必须把它与投递丢失区分开。
- 日志随运行实例增长，需要保留策略；清理过早会破坏跨代判定，保留过久占用工作区配额。

## 失效条件

- 若恢复机制不再销毁沙箱，或协议要求 Agent 对每条输入显式回执且控制面在同一事务内记录该回执，投递是否被消费对控制面重新可见，工作区日志不再是唯一跨代事实源。
- 若所有沙箱提供者的工作区持久化保证都退化为挂起后可能丢失写入，日志无法承担幂等状态，决策需要按提供者重新划分。
- 投递路径的 p99 延迟中工作区同步写入占比持续超过一半时，重新评估接受记录与消费记录的写入时机。
