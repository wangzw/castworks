# 投递幂等状态随工作区持久化

## 背景

事件投递的语义是至少一次（[ADR-wait-on-durable-inbox](adr-wait-on-durable-inbox.md)）：出站流会断连，看守进程会崩溃，沙箱会在代之间销毁重建，控制面副本会切换，投递与确认消息因此可能丢失，同一事件可能被重复投递。收件箱事件包括人类消息、外部系统事件、审批决定与内部通知；重复投递会使 Agent 重复执行工具调用或重复回复人类。

运行实例跨越多代沙箱。销毁重建后 Agent 以自身会话恢复机制续接，Agent 进程与看守进程的内存状态都不跨代保留；工作区是跨代保留的可写状态，Agent 的会话记录也位于工作区。重建后 Agent 是否已处理过某事件，取决于会话记录中是否保留了该事件的处理记录：工作区写入丢失或回退到上次快照时，会话记录中的处理随之消失。控制面数据库中的投递游标只反映控制面何时发送事件与何时收到确认，不反映 Agent 何时开始处理事件。确认丢失、看守进程在缓冲事件后崩溃，或沙箱在下一回合开始前被销毁时，控制面无法据此判断事件是否需要重新投喂。

事件是否已被 Agent 处理，这一事实必须有一个跨代可读且与 Agent 会话记录一同保留或一同回退的记录，判定才不会在每一代重新变得不确定。

## 考虑过的选项

### 只在控制面内存或数据库中去重

采用该选项意味着：控制面以 `(run_id, dedup_key)` 维护已投递集合，内存缓存由控制面副本持有，持久形态由控制面数据库承担；沙箱不保存投递状态。

**被拒**：控制面能够记录自己何时发送，不能记录 Agent 何时消费。确认在途丢失后沙箱被销毁时，控制面只能选择重投（Agent 已处理则重复）或不再投递（Agent 未处理则丢失），至少一次与跨代幂等无法同时成立。工作区日志由同处沙箱的看守进程在本地观察后写入，与 Agent 会话记录同处工作区。控制面的记录则依赖可能丢失的跨进程确认，也不随工作区写入的丢失或回退而变化；数据库中的投递记录与 Agent 的实际处理之间没有共同的观察点。

### 单级确认，收到即视为已消费

采用该选项意味着：看守进程收到 `Deliver` 即返回确认，控制面随后推进投递游标，该事件不再投递。

**被拒**：确认时事件只在看守进程的内存缓冲区中，没有跨代可读的持久记录；看守进程在确认后崩溃，或沙箱在投喂前被销毁时，事件既不会重投，也没有重喂的依据，至少一次退化为至多一次。

### 看守进程按日志自行重喂

采用该选项意味着：工作区内的日志同时保存事件内容，重建后由看守进程按日志重喂已接受、未消费的事件；控制面收到 `Accepted` 即越过该事件，不再从收件箱重投。

**被拒**：工作区写入丢失或回退到上次快照时，快照之后写入的接受记录连同事件内容一起消失，而控制面已经越过这些事件，它们既不在日志中，也不再被重投，事件因此丢失。日志保存事件内容还使工作区配额随收件箱流量增长。

### 投递意图日志随工作区持久化

采用该选项意味着：看守进程在把事件交给 Agent 之前，先在工作区内追加接受记录并同步写入持久存储；观察到 Agent 开始处理该输入后追加消费记录，消费记录同步写入完成后才发 `Consumed`，该写入不在投递路径上。确认分为 `Accepted` 与 `Consumed` 两级。`Accepted` 表示接受记录已同步写入工作区投递意图日志；此时事件尚未喂给 Agent，投喂责任由看守进程按日志承担。`Consumed` 只针对作为下一条用户消息的投递发出，表示 Agent 已开始处理对应输入，以回合开始为准；不提供回合信号的 Agent 以事件交给 Agent 为准。回合内投递（工具结果与权限决定）的消费只记入日志，不发 `Consumed`，其观察点由看守进程的设计定义。重建后由控制面从已记录的消费位置之后、以收件箱中的事件重投，看守进程按日志去重：日志已记消费的不再喂给 Agent，已接受未消费的带重新投递标记重喂。

**采用**，见决策。

## 决策

采用工作区内的投递意图日志承载投递幂等状态，该状态跨代有效；投递确认分 `Accepted` 与 `Consumed` 两级；重建后由控制面从收件箱重投，看守进程按日志去重。

## 后果

投递的重复判定在代之间保持一致：重建后由控制面重投，看守进程按工作区日志去重，不需要从控制面重建去重状态。日志与 Agent 会话记录同处工作区，工作区回退到上次快照时日志与 Agent 会话记录一同回退。重喂的判定与 Agent 续接后的会话一致，例外是丢失沙箱发生在消费记录写入之后、Agent 会话记录持久化该输入之前的情形：日志已记消费，该输入不再重喂。

本决策使项目承担以下义务，穷举如下：

- 看守进程在接受记录同步写入完成之后才回 `Accepted` 并把事件交给 Agent；写入失败时不得回 `Accepted`，也不得把事件交给 Agent。消费记录同步写入完成之后才发 `Consumed`；写入失败时不得发 `Consumed`。
- 看守进程只为作为下一条用户消息的投递发 `Consumed`，向控制面报告的已消费位置只计这类投递；其余投递（例如回合内投递）的消费只记入日志。这类投递若推进控制面的消费位置，该位置会越过已接受、尚未喂给 Agent 的事件，这些事件随后不再重投。
- 看守进程必须让控制面得知一批投递在按日志去重之后是否仍会交给 Agent：去重只在看守进程内发生，控制面无法自行判断投递之后 Agent 是否会开始处理。
- 重建后，控制面的重投起点以看守进程按日志报告的已消费位置为准：工作区回退到上次快照时，控制面记录的已消费位置随日志回退，但不低于已确认持久化的位置；已接受位置只按日志报告前进，不回退。
- 事件的跨代重投由控制面从消费位置之后发起，`Accepted` 不终止重投；看守进程按日志去重，并让重投的事件携带重新投递标记，使 Agent 侧可以识别可能重复的输入。
- 收件箱事件在不再可能被重投之前不得清理，重投的事件内容只能来自收件箱。
- 看守进程必须为回合内投递（工具结果与权限决定）定义 Agent 开始处理的观察点。
- 工作区布局必须为平台状态留出位置，日志与 Agent 自身状态一同保留；工作区清理、配额与快照策略不得把日志排除在持久化范围之外。
- `durableDir` 以外的工作区承载方式（例如共享文件系统、块存储与外部 CSI 卷）必须提供同步写入的持久化语义；Substrate 提供者以 `durableDir` 承载工作区的退化配置（[REF-substrate](../references.md)）不满足该语义，其后果列入代价；持久化确认的差异由工作区模块承担。
- 控制面分别维护已接受与已消费的位置，确认协议必须区分 `Accepted` 与 `Consumed` 两级。

承担的代价穷举如下：

- 每次投递在交给 Agent 之前同步写入接受记录，投递时延不低于这次写入的时延。作为下一条用户消息的投递另有一次消费记录的同步写入，不在投递路径上，`Consumed` 因此晚于 Agent 开始处理。同步写入完成前崩溃时 `Consumed` 尚未发出，已被 Agent 处理的事件可能带重新投递标记重喂。
- 回合内投递（工具结果与权限决定）不推进控制面的消费位置，重建后随重投再次送达看守进程，日志未记消费的事件带重新投递标记重喂。
- 正确性依赖工作区的持久化保证。以 `durableDir` 承载工作区时，上次快照之后的工作区写入可能丢失，日志与 Agent 会话记录一同回退到上次快照。快照之后已执行的外部副作用可能随重喂再次发生，只能依靠重新投递标记与 Agent 侧的幂等容忍重复。
- 收件箱的清理受重投范围约束：以 `durableDir` 承载工作区时，跨代可确认的消费位置只在同步挂起完成时前进，两次挂起之间已消费的事件不能清理。
- 投递幂等状态不能由控制面单独查询：控制面只持有消费位置，判断某个输入是否已被 Agent 处理需要读取工作区内的日志，运维与排障因此依赖看守进程或其上层接口。
- 已接受未消费是常态而非故障，对账与告警必须把它与投递丢失区分开。
- 日志随运行实例增长，需要保留策略；清理过早会破坏跨代判定，保留过久占用工作区配额。
- 消费记录以回合开始（不提供回合信号的 Agent 以事件交给 Agent 时）为准，早于 Agent 会话记录对该输入的持久化。此后、会话记录持久化之前丢失沙箱时，日志已记消费的事件不再重喂：Agent 只收到回合被中断通知，没有会话恢复能力的 Agent（例如 L0）因而失去该输入的内容。

## 失效条件

- Agent 的会话状态改由工作区以外的存储承载时，日志与会话记录不再一同保留或回退，本决策的依据不再成立。
- 托管的 Agent 能对每条输入把处理回执与处理本身一起原子地写入控制面可直接读取的持久存储（不经看守进程中转）时，消费事实可由控制面直接判定，工作区日志不再是唯一的跨代事实源。
- 跨代恢复后持续出现日志记为已消费而 Agent 会话记录却不含对应输入的事件时，日志与会话记录一同保留的前提不成立。
- 某个沙箱提供者的默认工作区配置不能提供同步写入的持久化语义时，本决策对该提供者不成立，需要为它另定幂等状态的承载方式。
- 工作区同步写入使投递路径持续达不到解冻路径的时延目标（事件到达至 Agent 可接收 p95 < 200 ms），且把多条接受记录合并为一次同步写入仍不能达到时，本决策不再成立。
