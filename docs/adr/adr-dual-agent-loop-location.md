# 同时支持沙箱内完整 Agent 与控制面外置循环

## 背景

托管的 Agent 是完整的第三方 Agent（Claude Code），它需要进程、文件系统、工具与自身的会话恢复机制，并以无头模式通过 stream-json 驱动（[REF-claude-code-headless](../references.md)）。这类 Agent 不能简化为一次模型调用；它的回合、工具、权限询问与会话状态都由沙箱内进程产生。

另一类工作负载是平台原生 Agent：模型循环可以运行在控制面，沙箱只承担工具执行（exec、文件读写、流式输出、后台作业）。把这类循环也塞进沙箱，就要求把 Agent 运行时重新打包进镜像，并把模型循环与沙箱生命周期绑在一起。

两类循环向运行实例状态机发出的事件、投递语义与挂起/恢复规则应当一致；否则收件箱、投递确认、唤醒谓词与恢复准入要为每种循环各写一套。

## 考虑过的选项

### 只支持沙箱内完整 Agent

采用它意味着所有 Agent 都以进程形式运行在沙箱内，控制面只驱动看守进程。**被拒**：平台原生 Agent 的模型循环无法运行在控制面，必须把运行时打包进沙箱；模型循环与沙箱生命周期耦合，轻量 Agent 也要付出完整沙箱的启动与镜像成本；控制面无法复用同一套工具执行接口。

### 只支持控制面外置循环

采用它意味着 Agent 的模型循环全部运行在控制面，沙箱只提供工具执行。**被拒**：Claude Code 需要完整的进程、文件系统与会话恢复机制，不能拆成控制面循环加工具调用；重新实现 Claude Code 的会话与工具语义超出托管环境的职责；已有的第三方 Agent 无法接入。

### 两种循环位置并存，统一驱动器接口

采用它意味着进程驱动器在沙箱内驱动 Claude Code，控制面循环驱动器在控制面运行原生 Agent 循环并通过看守进程的 `ToolExec` 接口使用沙箱；进程驱动器与控制面循环驱动器向 `runcontroller` 发出同一套事件。**采用**：见决策。

## 决策

采用两种 Agent 循环位置：进程驱动器在沙箱内驱动完整的第三方 Agent，控制面循环驱动器在控制面运行原生 Agent 循环并通过看守进程的 `ToolExec` 接口使用沙箱；进程驱动器与控制面循环驱动器共用同一套 Agent 驱动器接口、协议事件、投递语义与挂起/恢复规则。

## 后果

本决策使项目承担以下义务，穷举如下：

- Agent 驱动器接口是两种循环的唯一翻译层。两种驱动器必须使用同一套事件，包括回合开始与结束、工具开始与结束、权限询问、等待开始、定时请求与后台作业变化。某种循环没有对应来源的事件不发出（例如控制面循环没有自唤醒源，不发出自唤醒条目变化）。
- 在同一代沙箱内，进程驱动器必须保持 Agent 进程跨回合存活，使用 stream-json 输入输出。以挂起为目的的回合边界销毁按挂起规则关闭 stdin、令 Agent 正常退出，重建后以恢复句柄续接会话。控制面循环驱动器不得假定沙箱内存在 Agent 进程。
- `ToolExec` 必须提供 exec、文件读写、流式输出与后台作业，语义与沙箱内工具一致；帧经看守进程已认证的出站流传输，控制面循环驱动器不持有运行实例令牌。
- 投递、两级确认、唤醒谓词、挂起决策与恢复准入不得依赖循环位置；两种循环使用同一套收件箱、唤醒信号与恢复句柄语义。
- 两种驱动器共用同一套 Agent 驱动器接口；接口变更必须同时覆盖两种驱动器。

承担的代价穷举如下：

- 两套驱动器要实现与测试；控制面循环是第二条执行路径，有独立的失败模式。
- `ToolExec` 成为跨进程执行接口，工具调用的时延与鉴权进入控制面循环的关键路径。
- 控制面循环不能依赖 Agent 原生的会话持久化，必须自行持久化循环状态。
- 两种驱动器的事件语义可能漂移，必须用同一套契约测试约束。

## 失效条件

- Claude Code 能以库的形式嵌入控制面，且不丢失进程级隔离与文件系统语义时，沙箱内进程驱动器不再必要。
- 平台原生 Agent 能完整打包为沙箱进程且没有能力损失时，控制面循环驱动器不再必要。
