# 协议版本按代固定，两端支持当前与前一版本

## 背景

控制面由多个副本组成，升级时逐个替换副本；[出站流](../glossary.md)重连时 `Hello` 可能到达任一副本，接收副本接管[运行实例](../glossary.md)的所有权（[ADR-single-writer-per-run](adr-single-writer-per-run.md)）。滚动升级期间，同一时刻存在支持不同版本区间的副本。

[看守进程](../glossary.md)随沙箱镜像发布，一代沙箱内看守进程的二进制不变。[快照](../glossary.md)恢复不递增[代](../glossary.md)，恢复出来的是快照时刻的看守进程，它可能早于此后发布的若干版本（[ADR-generation-fencing](adr-generation-fencing.md)）。

看守进程发往控制面的消息跨连接按原内容重放（[ADR-asymmetric-stream-replay](adr-asymmetric-stream-replay.md)）：在一条连接上编码的消息，要在同一代的下一条连接上解码。

两端版本不一致时，握手与关闭消息仍须能被对方解码，否则双方连“不支持对方的版本”这件事都无法告知对方。

## 考虑过的选项

### 每条连接各自协商版本

采用它意味着每次 `Hello` 都重新协商，看守进程以自身支持的最高版本发起，控制面按自身区间应答，版本只降不升。**否决**：同一代的两条连接可能落到版本区间不同的副本上，协商出不同的版本；重放的消息却是按上一条连接的版本编码的，新连接上的接收方不一定能解码，同一代内的消息语义也会在两条连接之间改变。

### 两端只支持同一版本

采用它意味着控制面与看守进程的版本必须相等，不相等即拒绝。**否决**：滚动升级期间副本的版本本来就不一致，从快照恢复的看守进程又早于升级；每次发布都会使全部正在运行的代与全部快照失效。

### 新增可选消息与可选行为也递增版本

采用它意味着任何协议变化都递增版本号。**否决**：支持窗口只有两个版本，每递增一次，就有一批看守进程落到窗口之外，只能经重建恢复；可选的新增内容本可由不使用它的旧看守进程照常运行，却要为它付出重建的代价。

### 版本按代固定，两端支持当前与前一版本，可选扩展以能力标识引入

采用它意味着本代首次接受 `Hello` 时确定版本与能力并持久化，同代此后的连接一律沿用；两端各自支持当前版本 N 与前一版本 N−1；握手与关闭消息使用不随版本变化的固定格式。**采纳**，见决策。

## 决策

采用按代固定的协议版本：

- 握手消息（`Challenge`、`Hello`、`HelloAck`）与关闭消息（`Fenced`、`Shutdown`、`Close`）使用固定格式，字段只增不改，不随 `protocol_version` 变化，任何版本的两端都能解码。
- `Hello` 携带看守进程支持的连续版本区间与能力标识。本代首次接受 `Hello` 时，控制面取双方区间交集中的最大值与双方能力标识的交集，写入 `run.protocol_version` 与 `run.protocol_caps`，经 `HelloAck` 返回；同代此后的 `Hello` 一律沿用已落库的值。落库版本高于接收副本支持的上限，或接收副本不支持落库能力中的某一项时，该副本只是在滚动升级中较旧，以可重试关闭断开，看守进程重连到其他副本。
- 控制面与看守进程各自支持当前版本 N 与前一版本 N−1。发布顺序固定：控制面先升级到支持 N，再发布最高版本为 N 的镜像。
- 版本不支持的情形穷举为：本代首次协商时双方没有公共版本；落库版本低于接收副本支持的下限，即控制面已不再支持该版本；看守进程携带的区间不含落库版本。这些情形按版本不支持关闭，并以当前镜像重建沙箱（[ADR-unrecoverable-stream-failure-rebuilds-sandbox](adr-unrecoverable-stream-failure-rebuilds-sandbox.md)）。
- 新增可选消息种类或可选行为以能力标识引入，不递增版本，只有 `HelloAck` 返回的能力才可使用；改变既有消息的语义、删除消息或改变信封才递增版本。

## 后果

本决策使项目承担以下义务，穷举如下：

- `run` 表保存本代的协议版本与能力标识，代递增时清空。
- 控制面的每个副本同时实现 N 与 N−1 两个版本的编解码与消息语义。
- 发布流程保证控制面升级到支持 N 先于最高版本为 N 的镜像发布。
- 接收方据以改变传输、确认或运行实例状态机行为的字段是取值闭集，越出闭集按协议违规处理；只影响预测、指标、呈现等软输入的字段是开放集合，新增取值不递增版本，接收方按该字段规定的默认处理不认识的取值。开放集合的新取值在接收方认识之前，它要表达的区分随之丢弃，因此新取值先随控制面发布，再进入看守进程镜像。

承担的代价穷举如下：

- 版本早于 N−1 的看守进程（例如从旧快照恢复的）不能继续运行，只能经作废重建，其内存状态随之丢失。
- 同一代内版本不随控制面升级提升：存续时间长的代一直使用首次接受 `Hello` 时的版本，直到下一代；控制面不再支持该版本之后，该代在下一次 `Hello` 时按版本不支持重建，即使看守进程本身支持更新的版本。
- 滚动升级期间，落到较旧副本（不支持本代版本或能力）上的连接要多一次断开与重连。
- 两个版本并存，控制面的实现与测试负担随之增加。

## 失效条件

- 快照保留期或代的存续时间长于两次递增版本的间隔，使从快照恢复的看守进程经常落在 N−1 之前而触发重建时，两个版本的支持窗口不再够用。
