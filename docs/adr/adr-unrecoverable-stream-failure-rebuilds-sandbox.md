# 出站流不可恢复的失败以作废本代沙箱并重建收场

## 背景

[出站流](../glossary.md)的大多数中断靠重连恢复。有几类失败在同一[代](../glossary.md)内重连也不会消失：

- 协议违规：消息校验失败，或序号出现缺口。传输有序，看守进程到控制面的消息又从已提交的位置之后重放，缺口只能来自实现缺陷（[ADR-asymmetric-stream-replay](adr-asymmetric-stream-replay.md)）。
- 版本不支持：看守进程与控制面在本代没有可共同使用的版本，情形的穷举见 [ADR-protocol-version-pinned-per-generation](adr-protocol-version-pinned-per-generation.md)，例如首次协商时双方区间没有交集，或从旧[快照](../glossary.md)恢复出来的看守进程所在的代，其落库版本已低于控制面支持的下限。本代版本高于接收副本支持的上限只说明该副本在滚动升级中较旧，换副本重连即可恢复，不属于版本不支持。
- 认证失败：看守进程出示的令牌或持有证明不被接受，例如令牌到期时刻早于接受下界，或新代状态下令牌已过期；认证失败的连接上不会下发新令牌，同代重连时看守进程出示的仍是同一张令牌与同一个实例密钥（[ADR-run-token-audience-and-holder-binding](adr-run-token-audience-and-holder-binding.md)）。

同一代内重连，看守进程还是同一个进程：它的二进制、内存中的重放缓冲与接收状态都不变，本代的协议版本也已固定（[ADR-protocol-version-pinned-per-generation](adr-protocol-version-pinned-per-generation.md)）。

[看守进程](../glossary.md)是[沙箱](../glossary.md)的 PID 1，退出即沙箱退出；沙箱提供者把沙箱退出按沙箱丢失上报，控制面据此作废本代并以新代重建，新代从持久化状态对账继续（[ADR-warden-is-pid1](adr-warden-is-pid1.md)）。[运行实例](../glossary.md)必须能在没有人工介入的情况下从中断中恢复（[ADR-state-based-reconciliation](adr-state-based-reconciliation.md)）。

认证失败的连接不能证明来自本代沙箱：被替换的沙箱，以及取得过令牌与 `lease_id` 等不记名值的一方，都能发起连接（[ADR-generation-fencing](adr-generation-fencing.md)）。

## 考虑过的选项

### 终止传输，看守进程停止重连并上报，运行实例按部署缺陷待人工处理

采用它意味着协议违规与版本不支持只终止传输、不发关闭消息，看守进程重连一次仍失败即停止重连并上报，运行实例停在原沙箱上等运维处理。**否决**：恢复依赖人工，违背无人工介入恢复的要求；停止重连的沙箱仍在运行，占用计算资源并持有工作区租约，直到控制面的连接宽限或流丢失判定到期才得到处置；不发关闭消息时，对端只看到流结束，无法与传输中断区分。

### 按可重试关闭处理，同代重连

采用它意味着协议违规与版本不支持都以可重试关闭断开，看守进程退避后重连。**否决**：同代重连不改变看守进程的二进制、内存状态与本代版本，版本不支持不会因重连消失，由看守进程状态引起的违规会随重放再次出现，重连只是在不收敛的循环里消耗资源。

### 认证失败同样作废本代

采用它意味着控制面收到认证失败的连接后也执行“本代沙箱作废”。**否决**：这条连接不能证明来自本代沙箱，据它作废本代，任何能连到出站流端点的一方都能让运行实例的当前沙箱被替换。

### 已认证流上的不可恢复失败作废本代，看守进程在不可重试的关闭后退出

采用它意味着控制面对已认证出站流上的协议违规与版本不支持发出关闭消息并作废本代、重建沙箱；看守进程收到或发出不可重试的关闭后退出，沙箱随之退出。**采纳**，见决策。

## 决策

采用以作废本代沙箱并重建结束不可恢复的出站流失败：

- `Hello` 认证通过之后的出站流上发生协议违规（含消息校验失败与序号缺口）或版本不支持时，控制面发出对应的关闭消息，执行“本代沙箱作废”并重建沙箱，运行实例在新代按状态对账继续。运行实例尚在等待新代沙箱的首个 `Hello`（新代状态）时发生的版本不支持按恢复失败处理，同样以当前镜像重建。
- 认证失败，以及 `Hello` 认证通过之前的协议违规，只关闭这条流并计数，不改变运行实例状态。
- 看守进程收到认证失败、版本不支持或协议违规的关闭，或自己判定对端协议违规时，停止工作区写入，强制终止 Agent 进程树，以对应的退出原因退出；处理完代失效（`Fenced`）与关停（`Shutdown`）之后同样退出。
- 消息处理遇到的暂时性错误不是协议违规：控制面本地重试有限次后以可重试关闭断开，看守进程处理控制面消息失败时不确认、断开重连。

## 后果

本决策使项目承担以下义务，穷举如下：

- 关闭状态的每一种都有对应的关闭消息：代失效、关停、可重试关闭、认证失败、版本不支持与协议违规；协议违规的关闭两个方向都可以发出，并指出触发违规的对向消息序号。没有收到任何关闭消息而流结束，一律按传输中断处理。
- 看守进程的退出原因是闭集，由 `warden` 定义，写入容器终止信息与看守进程日志的末行。
- 沙箱提供者把沙箱退出按沙箱丢失上报，控制面据此重建，不等连接宽限到期。
- `runcontroller` 限制同一运行实例因协议违规或版本不支持连续作废的代数，达到上限后按不可恢复失败的现有路径处理。新代状态下的版本不支持不计入这一上限，计入 `runcontroller` 的恢复尝试次数 `resume_attempts`，受 `N_resume` 约束。
- 控制面消息处理事务遇到数据库不可用、超时或锁等待超时时本地重试，至多 `N_handler_retry` 次，仍失败以可重试关闭断开；该消息未确认，由看守进程重连后重放。

承担的代价穷举如下：

- 一次协议违规的代价是一次完整的沙箱重建：Agent 进程与看守进程的内存状态丢失，进行中的回合按“回合被中断”续接。
- 实现缺陷若在每一代都触发违规，运行实例在达到连续作废的上限之前反复重建。
- 发生违规的沙箱随退出消失，排障只能依靠关闭消息携带的原因与序号、计数，以及看守进程的退出原因与日志。
- 控制面的认证配置出错时，看守进程逐个以认证失败退出并触发重建，重建出的沙箱同样认证失败；这类故障表现为反复重建，而不是停在原沙箱上。

## 失效条件

- 实测显示协议违规主要来自传输层的暂时性错误，而不是实现缺陷或版本不一致时，作废重建的代价高于同代重连，本决策不再成立。
