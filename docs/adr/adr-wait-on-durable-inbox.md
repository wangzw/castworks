# 在持久化收件箱上等待

## 背景

托管环境需要在 Agent 等待 LLM 响应、外部系统事件、人工审批或人类消息（为举例）期间释放沙箱的计算资源。这些等待的时长跨越秒级到天级，同一运行实例在不同时刻等待的对象不同。沙箱的生命周期短于运行实例：它可能在等待期间被冻结、快照或销毁重建，销毁后进程内状态不再存在，只有工作区与控制面持久化的记录跨越重建。

依赖解除可能发生在沙箱不可达、沙箱已被销毁或沙箱尚未恢复的时刻。事件可能先于对应的等待登记到达，可能在等待解除之后到达，也可能与挂起决策并发到达。挂起期间丢失一次唤醒，运行实例就停在挂起状态且无人推进。

Agent 的协作层级决定沙箱能提供多少信号：驱动器中介的 Agent（L1）只暴露回合开始与结束、工具调用与权限询问等边界信号；纯观测的 Agent（L0）不提供任何等待声明。托管环境不能以 Agent 配合声明等待为前提判断它是否在等待。

同一运行实例的等待可能同时被多个事件源解除。控制面需要在这些来源之间维持单一顺序，并且只在依赖确定解除后恢复沙箱；依赖未解除就恢复，沙箱会立即再次进入同一等待，继续占用计算资源。

## 考虑过的选项

### 按等待类型各设通道

采用它意味着人类消息、外部系统事件、人工审批与 LLM 响应各自拥有独立的队列、唤醒路径与恢复入口，控制面按类型分别跟踪等待与解除。**被拒**：每种等待类型需要各自的持久化、去重、顺序与恢复逻辑，新增一种等待就新增一条通道；同一运行实例在多种等待之间切换时，控制面需要跨通道合并状态，挂起决策要分别判断每条通道，唤醒与挂起并发时的丢失风险随通道数量增长；L0 与 L1 Agent 无法区分许多等待类型，按类型划分的通道在信号不足时没有对应的事实来源。

### 沙箱以消息声明等待

采用它意味着看守进程或 Agent 驱动器把当前等待作为一条消息上报控制面，控制面以这条声明作为等待的事实。**被拒**：声明与控制面可观察的事实之间会出现分叉：沙箱在消息发出前被冻结或销毁，声明缺失；消息从旧代沙箱到达，声明已经过期；事件在声明之前到达，控制面没有等待可供挂靠。挂起决策依赖一个在等待期间不可达、可能已不存在的组件的上报，恢复时机因此不可判定；不具备声明能力的 Agent 得不到支持。

### 沙箱内自行轮询

采用它意味着等待期间沙箱保持运行，由沙箱内的进程周期性检查外部系统或收件箱，条件成立后继续执行。**被拒**：沙箱在等待全程占用计算资源，挂起释放资源的目的落空；等待期间的外部访问需要沙箱内持有凭据，与沙箱不持有长期凭据的约束冲突；轮询间隔决定响应延迟，轮询次数随等待时长线性增长，外部系统需要承受与等待时长成正比的请求量；轮询观察到的状态不构成持久事实，沙箱销毁后该观察丢失。

### 持久化收件箱与唤醒信号上的派生等待

采用它意味着控制面把可投递事件写入每个运行实例的持久化收件箱，把不进入收件箱的解除信号记为唤醒信号；运行实例的等待不是沙箱上报的对象，而是控制面依据持久化事实推导出的条件集合，唤醒谓词在持久化事实之上评估。**采用** — 见决策。

## 决策

采用「持久化收件箱 + 唤醒信号上的派生等待」作为唯一等待原语。运行实例的等待由控制面从持久化事实推导：可投递事件进入持久化收件箱，回合中的阻塞由唤醒信号解除；沙箱不上报等待，L1 Agent 的等待同样由控制面依据驱动器边界信号与已持久化的登记推导。全部等待类型共用这一原语，新增等待类型表现为新增事件源或唤醒信号来源，而不是新增等待机制。

## 后果

本决策使项目承担以下义务（穷举）：

- 全部控制面事件源必须通过统一摄入契约写入控制面，不得在沙箱内或旁路通道上自行解除等待。LLM 网关、连接器与人类通道因此都成为控制面的写入者；看守进程的本地代理信号经出站流上报，由 `runcontroller` 落为唤醒信号。
- 每次事件或信号写入，以及每次挂起决策，都必须依据持久化事实重新评估唤醒谓词；漏掉任一调用点，会出现事件已在收件箱而运行实例仍被挂起，或依赖已解除而挂起照常执行。
- 每个等待条件必须能在控制面持久化为可判定的事实。控制面看不到的阻塞不能作为等待条件，这类 Agent 交互不在支持范围内。
- 至少一次投递成为基线：收件箱事件可能在确认之前被重复投递，去重责任落在跨代持久化的投递状态上，见 [ADR-delivery-intent-log](adr-delivery-intent-log.md)。

承担的代价穷举如下：

- 每次事件或信号写入都触发一次唤醒谓词评估，评估与运行实例的持久化记录串行化。单运行实例的事件风暴会让控制面数据库成为唤醒延迟的关键路径，扩容受同一运行实例的写入串行化限制。
- 唤醒延迟由控制面的写入事务、恢复准入与沙箱重启共同决定，沙箱无法自行解除自身等待。对亚秒级的依赖解除，这条路径的延迟高于沙箱内直接继续执行。
- L2 协作式 Agent 的显式等待声明只能追加条件，不能替代或覆盖推导结果。驱动器必须把 Agent 的原生信号翻译为控制面可判定的事实，未覆盖的 Agent 行为表现为等待判定不到。
- 等待判定需要周期性对账，纠正写入、挂起与恢复并发时的遗漏。控制面因此多出一条持续运行的对账路径。
- 控制面承担全部等待状态的持久化与顺序责任。事件源之间的写入顺序不受控制面协调，正确性依赖收件箱的全序与去重键，而不是写入者的到达顺序。

## 失效条件

- 单运行实例的事件写入速率使唤醒谓词评估的 P99 延迟超过恢复延迟目标，且无法通过拆分该运行实例的写入路径缓解。
- 出现无法在控制面持久化为事实的阻塞类型，且使用该阻塞的工作负载无法通过回合边界或订阅转化。
- 投递重复使同一外部操作被执行两次，且跨代去重无法将该情形消除。
